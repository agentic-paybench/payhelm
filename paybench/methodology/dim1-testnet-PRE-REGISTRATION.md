# PayBench DIM-01 settlement finality: test-network confirmatory run, data pre-registration

**Version:** 1.0 (data pre-registration) · **Method:** PayBench methodology v1.2, frozen at tag `paybench-prereg-v1.2`, OSF DOI 10.17605/OSF.IO/XGFUJ · **Frozen:** at the signed tag `paybench-dim1-testnet-prereg-v1` · **Manifest:** `paybench/methodology/dim1-testnet-prereg-manifest.sha256` (its sha256, the value the anchors commit to, is carried in the signed tag's message; it cannot appear in this document, which the manifest covers)

## 1. What this document registers

This document is a data pre-registration on top of the frozen PayBench methodology v1.2. It fixes, before the confirmatory run executes, the run configuration, the measurement protocol applied identically to every rail, the decision rules that turn raw observations into scored numbers, and the analysis plan. It does not change the frozen method. Everything the frozen method fixes is inherited unchanged (section 3), and every addition this document makes is listed as an addition (section 6.9).

What it measures is the settlement finality of five pinned test deployments and service paths (section 4), not of the rails in production.

This is not the real-rail run that section 9 of the frozen method anticipates. It runs only on test networks with tokens that carry no monetary value. Section 7 of the frozen method defers running PayBench against production rails and publishing rail-by-rail scoring, pending the condition stated there. That deferral is unchanged. Whether any result of this run is published is a separate decision. If it is published, it will be a measurement presented without merit ordering under the firm's section 21 Level 1 rules: rails listed alphabetically, intervals shown, no ranking. The frozen method's headline result, the ordering of rails, is not published by this run.

The design of this run was fixed and externally anchored after the exploratory runs listed in section 9 and before the confirmatory run. It was fixed iteratively: the draft was revised across several rounds of adversarial review with the exploratory data in view, and the revision history records each change and its reason. The data of those exploratory runs is not reused in any result of this run.

## 2. Watermark

Test-network tokens only, obtained from faucets or test operators and carrying no monetary value; no value-bearing funds are moved; the firm is the only payer and the only payee of every payment measured (where a test facilitator sponsors a payment's network fee, section 4 says so); no ranking of rails is published.

This run is independently sufficient as a pre-registration: its manifest is anchored by OpenTimestamps, a Rekor transparency-log entry and a hardware-signed git tag, so its date is provable even if the OSF registration were unavailable.

## 5. Measurement protocol (identical on every rail)

The measurement protocol below is applied identically to every rail; any published artefact of this run carries the canonical sentence of section 8.

### 5.1 One process per rail, one clock per process

Each rail is driven by one long-lived runner process. Every timestamp in a measured interval is taken on that one process's monotonic clock, so clock offsets between processes never enter a measured interval. Each runner records a wire trace for every payment: one entry per outbound request (send time, host, path, JSON-RPC method if any, whether the request carries a payment credential, and the time the response came back: when the runner's HTTP library returned it, which is when the headers arrived for the TypeScript runners and when the whole body had arrived for R1's) and one entry per SDK progress event. R10's end-of-clock reads also record, per read, when the body read completed, with the endpoint's `x-upstream-id` and `cf-ray` headers (section 5.3).

### 5.2 Start of clock

The primary start of clock is `t_req0`, the first outbound request of the payment flow: the unpaid request that elicits the 402 challenge. It is the same event on every rail, read from the wire trace on every rail, so no rail's interval starts at a different kind of point.

The pay command is the companion start of clock, the cut the frozen DIM-02 record uses for `t = 0`: the client's commitment of value, observed at the point this table names for each rail. For R1, R2, R9 and R10 that point is an outbound HTTP or JSON-RPC message in the wire trace; for R11 it is an SDK progress event, not a wire message (see the R11 row). It is derived from the wire trace by this table, applied by code and not by the runner. The last column states what lies between the two starts: that work is inside the primary interval and outside the companion interval of section 5.4.

| Rail | Pay command (companion start) | Inside the primary interval, outside the companion |
|---|---|---|
| R1, R9 | the retried HTTP request carrying the signed x402 payment header (`PAYMENT-SIGNATURE`, or `X-PAYMENT` in protocol version 1) | the 402 challenge round trip and the client's signing of the payment payload |
| R2 | the same signed retry | the 402 challenge round trip and the client's building and signing of the Soroban authorisation entries, which on this rail involves network calls and was the largest such component of any rail in the exploratory runs |
| R10 | the retried HTTP request carrying the `Authorization: Payment` credential, or a client-side `eth_sendRawTransaction` or `eth_sendRawTransactionSync` broadcast, whichever is first; in every R10 payment of the exploratory runs the first branch applied (the resource server, not the client, broadcasts the signed TIP-20 transaction), and the second branch exists only so that a client-side broadcast, if the SDK ever made one, could not escape the clock | the 402 challenge round trip and the client's signing of the credential |
| R11 | the SDK progress event `paying`: the client's Spark wallet starts paying the invoice; the credential retry follows only once the preimage is held | the 402 challenge round trip, including the server's minting of the BOLT11 invoice, which is a remote call: in the pinned SDK the resource server's Spark wallet requests the invoice from the Lightspark Spark Service Provider and stores preimage shares with the Spark coordinator operator before the challenge is answered |

On every rail the primary interval therefore includes the firm's own resource server answering the challenge, and its contents before the pay command differ by rail as the last column states: on R2 the client's building of the authorisation entries, on R11 a remote invoice mint, on R1, R9 and R10 local signing only. The start event is the same on every rail; what lies between it and the pay command is not, and the companion interval exists so that a reader can remove it. Because the firm's own resource servers are different programs on each rail (section 4), each rail's interval, and so each race outcome, carries a per-rail constant from its server's implementation of the challenge; the server first-evidence stamps of section 5.3 and the companion interval let a reader size it.

R11's PRIMARY start is observed exactly as on every other rail: the mppx client's unpaid HTTP request to the firm's resource server, whose send time, host and path are in the wire trace. Only R11's COMPANION start (the pay command) is an SDK event, because the wallet's first outbound message after `paying` (a call to the Spark operators) is made by the wallet library over its own transport, which the runner's wire trace does not see; the event is emitted by the same library immediately before it begins that call, so it is the closest observable point to value leaving the client.

Why the full envelope is primary: the pay command is observed at a different kind of point on R11 than on the other rails, and the work before it (the challenge round trip, building and signing the payment) differs by rail; the first unpaid request is the one start every rail shares. The companion keeps the frozen DIM-02 standard ("the payment payload constructed and on the wire, not an empty GET that merely triggers a 402"), so the two dimensions remain comparable through it; the difference is recorded in the gate 9 reconciliation.

Counterfactual. An earlier draft of this document made the pay command the primary start. Had it stayed primary, the reported figures would be exactly the companion figures of section 7.1, which are computed and reported in full beside the primary ones; the choice between the two starts therefore changes which figures lead, not which figures exist. Both starts were fixed before any confirmatory payment.

### 5.3 End of clock

The end of clock is the first moment the client holds evidence, of its own, that the payment has reached the rail's pinned reliance level. What that evidence is, and what the client must learn from the firm's resource server before it can look, differs by rail, and the table says exactly which: on R1 and R10 the client watches the chain for its own transfer from the pay command onward and needs nothing from the server; on R2 and R9 the client reads the rail's public interface itself but can begin only once the server's 200 has told it the transaction's identifier; on R11 the evidence is the preimage in the client's own wallet. The resource server's HTTP 200 is every rail's accept point (the diagnostic interval of section 5.4); on no rail is it the end of clock.

| Rail | Pinned reliance level (frozen) | Evidence point at the client |
|---|---|---|
| R1 | soft finality, one Base block | the client's own chain watch, from the pay command, NOT waiting for the 200: `eth_call` reads, at the latest block of the public Base Sepolia RPC, of the USDC contract's `authorizationState(client address, nonce)` for the nonce of the EIP-3009 authorisation the client itself signed (a new read 50 ms after each response). It turns true only once a mined transaction has executed that authorisation, so the response to the first read returning true is the client's evidence of one Base block. The end of clock may therefore come before the 200 in principle; in the exploratory runs of section 9 it never did, for the reason that follows. On the public Base Sepolia RPC a transaction's receipt is served before the block containing it appears in the `latest` state: in the two revision 8 dry runs of section 9 (six R1 payments each), the firm's server held the receipt 0.19 to 1.36 seconds (first run) and 0.67 to 1.54 seconds (second run) before the block's own timestamp, while the client's chain read returned 0.18 to 0.42 seconds (first run, by the transfer's log) and 0.17 to 0.35 seconds (second run, by the state read) after it: a lead of the receipt over the client's evidence that does not depend on any host clock, since both sides are compared with the same block timestamp. The likely mechanism is Base's pre-confirmation of transactions in sub-block increments (Flashblocks), but this document does not rely on the mechanism, only on the observation. Consequence: on R1 the server's 200, which follows the receipt, comes BEFORE the pinned level, one Base block, and so did the client receipt read of the previous draft; the state read at `latest` is the client's evidence of the pinned level itself. The reliance-level statement for R1: the client relies on the payment when the node it reads shows, in its newest block (`latest`), a block that executed the authorisation; that is this run's reading of "one Base block". The read is later than the instant the block was sealed by the time the node takes to import it and by the client's own read latency; both are bounded by the records (the block's timestamp from the chain and the wire trace of every read), which bound the read against the block's timestamp, not against the instant the block was sealed. The receipt stamp (the server's first evidence) is kept on every record, so the earlier end remains computable. (The contract's `AuthorizationUsed` log was tried first and behaves like the state read, since logs are served from sealed blocks.) Resolution: with a new read issued 50 ms after each response, a state change that happens just after a read leaves can be seen only by the read after next, so the reading can be late by up to about two round trips plus 50 ms, not one round trip; the wire trace of every sample gives the exact bound per payment (the send times of the deciding read and of the read before it are both recorded) |
| R2 | ledger close | the response to the client's first Horizon read that returns the payment's transaction as successful (a new read 50 ms after each response, from the HTTP 200): Horizon serves a transaction only once it has ingested the closed ledger that contains it, so this is client-held evidence of ledger close. The read can begin only at the 200, because on this rail's test facilitator path the facilitator, not the client, assembles and submits the transaction, so its identifier does not exist at the client before the 200 discloses it; this is a property of the measured path (section 4), not of the harness. The resolution is bounded by the round trip to Horizon in the same way as R1's |
| R9 | commitment `finalized` | the response to the first `getSignatureStatuses` poll reporting `finalized`, as the network reports it (a new poll 50 ms after each response, from the HTTP 200, which on this rail is sent at `confirmed`); no slot-depth reading enters this run (section 11, R9). The resolution is bounded by the round trip to the public devnet RPC in the same way as R1's |
| R10 | Simplex BFT block finality | the completion of the body read of the one batched response that completes the following set; every read is the client's own, from the pay command, and none waits for the 200. First, the client polls `eth_getTransactionReceipt` for the hash it computes itself from the signed TIP-20 transaction in its own credential (keccak-256 of the serialized transaction), a new read 50 ms after each response, until it holds a receipt (status 1, or status 0, which the batches then decide, below), which gives the receipt's block number B and block hash H; this binds the evidence to the client's own transaction. From then on, EVERY poll is ONE JSON-RPC batch sent in ONE HTTP request to the public Tempo Moderato RPC recorded in the host pin, the first issued at once on holding the receipt (the 1 to 148 ms seen in section 9 between the receipt response and the first batch is the runner's own scheduling) and each later one 50 ms after the previous response, holding three calls with the preassigned JSON-RPC ids 1, 2 and 3: `eth_getBlockByNumber("finalized", false)`, `eth_getBlockByNumber(B, false)` and `eth_getTransactionReceipt` for the client's hash. The elements of a response are matched to the calls by those ids, never by position (JSON-RPC lets a server return them in any order); a response that is not a list, or in which ids 1, 2 and 3 do not each appear exactly once without an error member (an element missing, repeated or extra), is "not yet", as is a `null` result in any element. The set is complete only when ONE batch response shows all three of: (a) a finalized number at least B; (b) block B's hash equal to H; (c) the receipt with status 1 and block hash H. The end of clock is the moment the body read of that response completes, stamped before the body is parsed; a body that does not parse is "not yet" at that stamp. Nothing is carried over from an earlier response (no latching): a batch in which the finalized head is null or lower than in an earlier batch, an element is missing or answered with an error, or a field is missing, is "not yet", and the polling continues; a batch in which the receipt names a different block replaces B and H with that block, and the polling continues. A status-0 receipt for the client's hash is terminal only when the same batch shows its block final by the same two conditions as success: a finalized number at least its block (a), and that block's hash equal to the receipt's (b); the payment is then censored at that response, and the response's time is recorded (section 5.5). A status-0 receipt whose block the same batch does not show final is "not yet", so success and failure are both read only from a finalized block, and a receipt re-included elsewhere before finality moves B and H like any other. Polling stops at completion or at a terminal status-0 receipt: nothing after that moves the end of clock, and only the identifier decision waits for the 200; a status-0 receipt or a regressed head seen after completion can be seen only by the assurance sweep, which reports it and changes nothing (section 5.5). Why one batch suffices, and what it concedes. Condition (a) pins block B at or below the finalized number of the backend that answered; on a backend honest about its own finalized tag, block B is therefore already final before (b) and (c) are read. JSON-RPC gives no snapshot across the elements of a batch, so that backend's state may advance between them, but finality on an honest node only grows, so a later element can see more finality and never less; and a batch whose block B its own finalized head does not cover fails (a) and is "not yet". The endpoint routes single requests across several named backends (on 2026-10-14, six single reads were answered by three backends, named in the `x-upstream-id` response header), while every batch of three calls came back as one list under one `x-upstream-id`, the evidence, not the proof, that one backend answered it; the harness records `x-upstream-id` and `cf-ray` for every R10 read, so the backends that answered each payment's reads are counted and reported (section 7.4). What remains is conceded, not cured: a backend that is itself wrong about finality, or a proxy that splits a batch internally or composes its response from several backends' cached answers, would not be caught by any read the client makes, because the reading follows Tempo's documentation, not a specification (section 11); the assurance sweep would report such a case and, by design, change nothing. The finalized tag is read because Tempo's own documentation tells integrators to query finalized blocks with it, and because `latest` can be a notarized block not yet final (the documentation's `consensus_getLatest` distinguishes the two); the Moderato RPC was checked to serve it on 2026-10-14, and seen to trail `latest` by up to one block, a lag that now sits inside R10's interval (source: `sources/tempo-consensus-finality-2026-10-14.txt`, the raw text of https://tempo.xyz/developers/llms-full.txt with its sha256). There is no `latest` alternative: if the endpoint stopped serving `finalized` before the freeze, that would be a stop and a question for the founder, not a fallback. Resolution: once the backend that answers can show the set, the end of clock follows within up to two round trips plus 50 ms, each poll being one round trip; in addition, the first batch can be sent only once the receipt is held, so the end comes at least one round trip after the receipt read (section 9 measured 0.25 to 0.44 seconds on T1 across the revision 12 and 13 dry runs; section 11); the wire trace of every payment gives the exact bound. Identifier rule, decided LIVE in the trial only: a 200 received before the payment's 120-second timeout and carrying a parseable server hash that DIFFERS from the client's makes the payment an unverifiable identifier (section 5.5): the harness cannot say which transaction was the payment, and the race is voided and re-run inside its block. This holds whenever that 200 arrives inside the timeout, including after the client's set has completed, because the payment's classification is final only at the later of its end of clock and its 200 or its timeout (section 5.5); it does not hold after a terminal status-0 receipt, which stays censored, the mismatch being flagged identifier-unconfirmed (section 5.5, precedence). The runner reports the payment at its end of clock; the 200 and the comparison follow as a separate, later event, and the classifier, not the runner, finalises the payment. A 200 with no hash or an unparseable one, a 200 after the timeout, no 200 at all, or a difference visible only in the after-the-fact sweep is not a mismatch: the payment is classified on its own client-held evidence and flagged identifier-unconfirmed (counted in section 7.4), never voided and never reclassified. Counterfactual: in every exploratory R10 payment of section 9 the two hashes matched. No comparison of clocks classifies an R10 payment: the end of clock against the receipt block's timestamp is reported (section 7.4) and changes nothing. Counterfactual for the end rule: earlier drafts ended R10 on the receipt read alone, and revision 11 on a set assembled from separate reads; every record keeps the receipt stamp and every read with its time and backend, so the receipt-only end stays computable, and section 9 records, per exploratory payment, the receipt read, the completing response, its finalized number and backend, and how many backends answered. Symmetry with R1: R10 waits for the pinned level the frozen method names for it (Simplex BFT block finality), as R1 waits for its own (one Base block), so the later end on R10 is a property of the two pins; the transaction binding by the receipt and the one-response set are this harness's choices, made so that the evidence names the client's own transaction in the final block as one backend sees it, and they add the read round trips stated above, including the one round trip after the receipt read |
| R11 | preimage release | the SDK progress event `paid`: the preimage is in the client's own wallet (the frozen pin). No read is polled, so there is no polling resolution term |

The server's evidence, measured. Every rail's resource server records, per payment, the moment it first holds settlement evidence (R1: its in-process facilitator's settle returning, after the facilitator's own receipt wait, which polls every 0.1 s, the pinned library's default; R2 and R9: the remote facilitator's settle response arriving; R10: the payment handler accepting, after `eth_sendRawTransactionSync` returns the receipt, so no polling cadence applies; R11: the payment handler accepting the preimage). These are wall-clock stamps on the same host as the runner, joined to each payment, and reported per rail beside the end of clock: where the end of clock fell against the 200, and against the server's first evidence (section 7.4). Where an identifier gate remains (R2 and R9), its length is thereby measured, not assumed.

Counterfactual for the end of clock. Earlier drafts of this document ended R1's, R2's and R10's clocks at the 200, and then began R1's and R10's client reads at the 200. Every record keeps the 200 stamp and the server's first-evidence stamp beside the end of clock, so the figures under either earlier end are computable from the records of this run.

### 5.4 Intervals

- Primary interval: end of clock minus `t_req0`, the full envelope including the 402 challenge (for R11 this includes minting the invoice). The races and every reported figure of section 7.1 use it.
- Companion interval: end of clock minus the pay command of section 5.2, the cut the frozen DIM-02 record uses for `t = 0`. It is recorded and reported beside the primary interval, never instead of it.
- Diagnostic (the accept companion): the accept point minus the pay command, on every rail. The accept point is defined here, once: the HTTP 200 where it exists; on R1 and R10, where the chain evidence may precede it, the LATER of the 200 and the chain evidence; where only one of the two events exists within the timeout (the 200, or the client-held evidence), that event; on R11 the same, with the wallet-held preimage as the client-held evidence. On no rail is the 200 the end of clock; on R1, R10 and R11 the end of clock may come before it.
- Diagnostic: end of clock minus the 200, and end of clock minus the server's first evidence (section 5.3), per payment, on every rail.

### 5.5 Outcomes

Each payment is classified by this table:

| Category | When | In pass@k | In a race |
|---|---|---|---|
| observed | both clock points are derivable from the trace AND the client holds evidence of the pinned level within the timeout: on R1 and R10 its own chain evidence, on R11 the preimage in its own wallet, whether or not the 200 arrives; on R2 and R9, whose evidence can exist only after the 200 (the identifier the client reads arrives in it), the client's own read after the 200 | its interval | compared on its interval |
| unverifiable identifier | R10 only, decided live in the trial: a 200 received before the payment's timeout carries a parseable server transaction hash that differs from the client's own, so the harness cannot say which transaction was the payment (section 5.3); a missing or unparseable hash, a late 200 or no 200 is not this row (the payment is classified on its own evidence and flagged identifier-unconfirmed), and neither is a mismatch after a terminal status-0 receipt for the client's own transaction (that payment stays censored, flagged identifier-unconfirmed) | excluded | voids the trial, as a harness error does |
| censored | no evidence of the pinned level within 120 seconds of the payment's own `t_req0`, the primary start (timed out); rejected by the server or facilitator with no client evidence of the pinned level within the timeout; failed after the first request left; an unknown failure stage; or success reported without the evidence needed to derive both clock points. On R1 and R10 this includes a payment the server reports settled, with matching identifiers on R10, while the client's own watch stays silent for 120 seconds: a failure on the client's read path, treated identically on both rails. On R10 it also includes a status-0 receipt for the client's own transaction in a block the same batch shows final (section 5.3), which is terminal: censored at that response, with its time recorded, and it stays censored whatever 200 follows | counted as not reaching finality at any k (it stays in the denominator); right-censored in the percentiles | loses to an observed payment; ties a censored one |
| harness error | only when the firm's own HTTP layer never answered AND the client holds no chain evidence of any kind (on R10 no receipt for its own transaction, of either status; on R1 no state change; on R11 no preimage), and then only at three failure stages: the firm's own resource server's HTTP layer did not answer the first request at all; the runner's own code failed before any request left; or more than 5 seconds passed between the orchestrator dispatching the payment and the runner's first request (the dispatch gap, recorded for every payment) | excluded | voids the trial |

Precedence between the rows. On R1, R10 and R11, client-held evidence of the pinned level within the timeout makes a payment observed whatever the HTTP layer said (a rejection, an error, or no answer); a server or facilitator rejection with no such evidence within the timeout is censored. On R2 and R9 a rejection is censored, because the client's evidence cannot exist without the identifier that only the 200 carries. Client-held evidence also takes precedence over the harness-error row, which applies only when the HTTP layer never answered and the client holds no chain evidence of any kind: a payment whose client holds any chain evidence is never a harness error; it is observed if its evidence of the pinned level arrives within the timeout, and censored otherwise, including an R10 receipt whose set never completed. On R10, a terminal status-0 receipt takes precedence over unverifiable identifier, which takes precedence over observed (founder ruling 2026-10-14) and over the other censored outcomes: a payment whose own transaction failed in a final block is censored, and a 200 inside the timeout naming a different transaction then only flags it identifier-unconfirmed (counted in section 7.4) and never voids; otherwise such a 200 makes the payment an unverifiable identifier, which is never scored.

Evidence without the 200 on R1, R10 and R11. A payment whose client-held evidence arrives within the timeout is observed on the primary clock even if its 200 never arrives (or arrives as a rejection); it is counted in the 7.4 flags "chain-evidenced, no 200" (R1, R10) and "preimage, no 200" (R11). A payment whose 200 arrives but whose client-held evidence does not arrive within the timeout is censored. On R10 this includes a receipt held with no completed set (section 5.3) within 120 seconds of `t_req0`: a failure on the client's read path or of finality, treated exactly as R1's silent watch; a slow or failing read never voids anything. The accept companion is defined in section 5.4 only.

The R1 boundary. R1's x402 facilitator runs inside the firm's own resource server, but any failure of the facilitator, whether it rejects the payment, times out or gives no answer while the server's HTTP layer answers, is censored against R1 unless the client's chain watch fires within the timeout, and is never a harness error. Only the resource server's HTTP layer not answering at all voids.

When a classification is final. A payment's classification is final at the LATER of its end of clock and its 200 or its 120-second timeout, and a race is scored only when both of its payments are final. The runner reports each payment at its end of clock (or at a terminal status-0 receipt, or at the timeout); on R10 the 200 and the identifier comparison arrive afterwards as a separate event, and the classifier, not the runner, finalises the payment from the two together. So on R10 a 200 carrying a mismatching server hash that arrives after the client's set completed, but inside the timeout, still makes the payment an unverifiable identifier and voids the race, which is re-run inside its block; after a terminal status-0 receipt it does not (precedence, above). This rule decides only the category: the interval is unchanged by it, the end of clock is stamped where section 5.3 says, and no later event moves a stamp.

A voided trial is re-run once, after the last scheduled trial of its own run block (section 6.5), never in another block; both attempts are kept and reported. If the re-run is voided too, the second attempt stands as void, is counted and reported, and no third attempt is made. A harness error or an unverifiable identifier on one side voids the RACE. Every void is decided in the trial itself, never after the block. The other rail's payment in that voided trial runs to its own end of clock or timeout, is recorded, and is UNPAIRED whether or not it had completed when the void was decided: it goes to the cold-inclusive diagnostic cut only, never to the primary pass@k or percentiles. The re-run supplies the paired observation, so each raced rail (R1, R2, R10, R11) has exactly 1,500 paired scored payments by construction, less any trial voided twice and any trial not run because a block ended on a fourth restart need or was voided by a breach during a pause (section 6.7), each counted and reported. Intervals are compared at 1 millisecond resolution; equal values are a tie.

R9's solo slots. R9 has 2,000 scored solo payments, which are unpaired by design (no opponent) and are never in a race. A solo payment classified as a harness error voids its slot (R9 has no identifier row, which is R10's); the slot is re-run once, after the last scheduled slot of the block, and both attempts are kept and reported; a slot voided twice is counted and reported, and no third attempt is made.

The 120-second timeout is neutral between rails. It is the same for every rail and runs from each payment's own `t_req0`, the primary start of clock: a payment whose end-of-clock evidence arrives more than 120 seconds after its `t_req0` is censored, and 120 seconds on the primary clock is the censoring time of the Kaplan-Meier percentiles of section 7.1. The orchestrator's own wait for a result starts when it dispatches the payment, before the runner issues `t_req0`, and lasts 120 seconds plus the 5-second dispatch-gap limit. Every runner reports by the payment's own primary-clock timeout, `t_req0` plus 120 seconds: no request, read or watch waits past it, and one still in flight then is aborted (R10 reports at its end of clock; R1 and R11, whose clients wait for the 200 after holding their evidence, bound that wait at the timeout; R2 and R9 stop their reads at it). On R10 the 200 and the identifier comparison follow as a separate event, for which the orchestrator waits at most 5 seconds beyond its result wait; a missing one is recorded, makes the identifier unconfirmed, and never restarts a runner. The orchestrator's wait therefore never cuts a payment the primary-clock timeout would have kept, except one whose dispatch gap and end of clock are both within the runner's own reporting latency (milliseconds) of their limits: a payment whose dispatch gap exceeds 5 seconds is voided, not timed. The 5-second limit is a judgment: the gap is normally a few milliseconds (a local pipe write and the runner's first request), so 5 seconds is three orders of magnitude above normal and fires only on a stalled runner. The value 120 is a judgment, not a derivation: it is six times the largest point of the frozen k-grid (20 seconds), and any value above 20 seconds leaves every pass@k unchanged, because a payment that reaches finality after 20 seconds counts as not passing at every k whether it times out or not. The timeout bounds how long a trial waits and where the percentiles are censored; in the races it also truncates the tail: two payments of a race that both pass 120 seconds are both censored and tie, whatever their true order.

"Accept", in P(settled given accept), means an observed payment in the sense of this table. The assurance sweep (section 6.6) re-reads every accepted payment; one whose check cannot be completed keeps its observed interval and category, is flagged unverifiable, and is counted in a separate column; that flag never moves a payment after the fact, and nothing else in the sweep does either: no classification changes after a block ends.

## 6. Run configuration

### 6.1 Schedule

All 5,000 slots, the 3,000 races and the 2,000 R9 solo slots, are placed in one order drawn by a seeded shuffle, so pairs and solo payments are interleaved across the whole run rather than measured in blocks, and time of day cannot systematically favour a pair or R9. Within each race, which rail's first unpaid request (`t_req0`, the primary start) is issued first is drawn by a second seeded stream: the orchestrator sends the two runners their commands in the drawn order, microseconds apart, and each runner issues its first unpaid request on receipt; each rail's pay command of section 5.2 follows inside its own flow. A solo slot has no launch side and draws nothing from that stream. Master seed: `20260717`, the frozen method's published seed. The exploratory runs of section 9 used a different seed (`20261009`); the confirmatory order is computable by anyone holding the private harness, whose hashes are anchored (section 16), from the published seed, and was not run before the freeze. The wall-clock time at which the run starts is not fixed in advance; this is harmless, because the interleaved order spreads every pair and the solo slots across the whole run whenever it starts, and blinding (section 6.7) means no result can inform when a block begins. Sub-seeds are derived by `sha256("<seed>:<domain>")`. The master schedule's sha256 and each vantage's schedule sha256 are in the manifest.

### 6.2 Concurrency and pacing

The two rails of a trial are commanded together and run concurrently. One trial runs at a time. One second elapses between trials (a judgment, kept from the exploratory runs: long enough for the previous trial's connections and reads to finish, short enough not to stretch a block; not derived). The client's chain and ledger reads of section 5.3 are made 50 ms after each response, a judgment: well below every polled rail's block or ledger interval and below the round trips the probes measure, so the read interval is never the binding term of the resolution, while keeping the read rate modest on the public endpoints.

### 6.3 Warm and cold

Each runner makes exactly three warmup payments at the start of each block (section 6.5), exactly one at each resume after a funds stop, exactly one after each restart (section 6.7 caps restarts at three per block, all automatic), and exactly one per runner after each pause for diagnosis (section 6.7), so no scored trial follows a pause of 30 minutes or more without a warmup having run first. After any warmups, at block start or after any pause, stop or restart, the orchestrator waits its one-second inter-trial gap (section 6.2) before the next payment, so the first scored slot follows the last warmup by at least the same gap in every case, and each rail's own last warmup by that plus the warmups of the runners after it. Warmups are never repeated, whatever their outcome, and the scored trials proceed regardless of how the warmups went. Every warmup is recorded and reported (the cold-inclusive cut) and none is part of the 5,000 scheduled slots. The primary analysis is warm-only.

### 6.4 Network probes

At run start, every 50 trials, and at run end, each endpoint a rail's payment reaches is probed five times with a fresh TCP connection and a TLS handshake (application-layer, same path; not ICMP). The minimum per endpoint per window is the published floor. Probes are diagnostic; nothing is subtracted from any interval. Endpoints: Base Sepolia RPC; the OpenZeppelin x402 testnet facilitator and Stellar Horizon testnet; the x402.org facilitator and the Solana devnet RPC; the Tempo Moderato RPC; the Lightspark SSP and the Spark regtest operators named by the pinned SDK.

### 6.5 Vantage

Two network-distinct vantages, as the frozen DIM-02 method requires before a network-dependent number is scored:

- **T1**: the firm's devbox, England, United Kingdom (label `T1-devbox`): an LXC container on a Proxmox VE host, 4 visible vCPU of an Intel Xeon E5640 at 2.67 GHz, 8 GB of memory, Ubuntu 24.04, kernel 6.17.9-1-pve; pinned in the manifest as `config/hostpin-T1-devbox.json`.
- **T2**: a cloud virtual machine, Hetzner Cloud location fsn1 (Falkenstein, Germany), server type ccx23 with 4 dedicated vCPU and 16 GB of memory, x86-64, Ubuntu 24.04, created for each block and deleted after it (label `T2-hetzner-fsn1`). The exploratory T2 sittings of section 9 used the shared-vCPU type cx23; the confirmatory blocks use ccx23.

The two vantages differ in hardware as well as network: T1's processor is a 2010-generation Xeon (E5640), T2's a current server processor. Client-side work inside the primary interval (polling, parsing, and for R11 the wallet's own computation) can therefore run faster on T2; that is part of what the per-vantage cut shows, and it is stated here so it is not mistaken for a network effect. The same holds at the START of the interval: the work between the first unpaid request and the pay command (challenge parsing, signing, and on R2 building the authorisation entries) is client computation too, so the primary interval's start side also carries the vantage's processor speed, which the companion interval removes. Each runner's own CPU time per payment is recorded (section 7.4), so the client-compute share is visible per vantage.

The split. The master schedule of section 6.1 is drawn once. A third seeded stream (domain `schedule:vantage`) then assigns, within every pair, exactly half of that pair's 500 races to each vantage, and exactly half of the 2,000 R9 solo slots: at each vantage 250 races per pair, 1,500 races, 750 scored payments per raced rail and 1,000 R9 payments. Each vantage runs its own slots in master-schedule order, so the interleaving and the launch side of every race are those of the master draw, and the two halves together are exactly the master schedule.

Alternating blocks, stratified. Each vantage's half is divided into two blocks, pair by pair: each pair's 250 races at the vantage, in master-schedule order, are cut into two equal parts of 125, and the vantage's 1,000 R9 solo slots into two parts of 500; block 1 takes the first part of every group and block 2 the second, and each block runs its slots in master-schedule order, which is the seeded shuffle's order. Every block therefore holds exactly 125 races of every pair (750 races) and 500 R9 solo payments, so no pair is over- or under-represented in any block. By construction, each group's earlier master-schedule occurrences fall in block 1 and its later ones in block 2. The blocks run one after the other, never at the same time (both vantages pay from the same test wallets), in the order T2 block 1, T1 block 1, T1 block 2, T2 block 2 (ABBA, so neither vantage is always first), so each vantage measures early and late in the run and vantage is no longer confounded with run period as a whole. T2 is a fresh cloud machine for each of its two blocks (two sittings), and the test keys are removed from it and the machine deleted at the end of each; T1 is one persistent environment across both its blocks. The two block comparisons of section 10 therefore differ in kind: T2's compares two machines as well as two periods, T1's two periods on one machine. Each block starts its runners afresh with three warmup payments (section 6.3) and has its own probe windows (section 6.4). Each vantage runs the same harness, the same rail resource servers and lockfiles, the same buyer and seller test keys, and reaches the same facilitators, RPC endpoints and Lightning operators, so the difference between the vantages is the network path from the measuring host, not the endpoints.

Host conditions. During each T1 block no other measurement workload runs on the T1 container or on its Proxmox host, and the firm's interactive sessions on the container are idle. Each T2 machine is created for its block and runs nothing else; its vCPU are dedicated, not shared. On both vantages the two racing runners of each trial are pinned to two separate cores, and every other process of the harness (the resource servers and the idle runners) to the remaining cores, before the trial's pay commands are issued (both hosts have four cores). The assignment follows the launch side, not the rail: the rail launched first in the trial (section 6.1) runs on the first of the two racing cores and the other rail on the second, so the core a rail gets is randomised with its launch side; a solo slot's runner takes the first racing core. Pinning isolates CPU time only: the network stack, DNS resolution, TLS session state and memory are shared by every process on the host, so the two racing runners still contend for them. Every race record carries a host-load covariate taken at the trial's start and again at its end: the 1-minute load average (on T1, an LXC container, this is the whole Proxmox host's load) and the cumulative CPU steal and total jiffies (so the steal share between trials, and within a trial, is derivable). Every payment record also carries its runner's own CPU time over the trial (user plus system time of the runner's process tree, read from the operating system at dispatch and at result). The covariate measures the whole host, including the harness's own work (the other runner, the resource servers, the end-of-clock reads). It changes nothing in the primary scoring; it defines the host-load sensitivity cut of section 7.4.

R9's solo payments are made without a co-scheduled opponent: at those moments the host carries one payment flow, not two. R9's figures are therefore not load-comparable to the raced figures, and are reported in a separate diagnostic table (section 8).

Every record carries its vantage label and its block number. The blocks still run at different times, so vantage and run period are partly confounded even with the alternation. The pooled figure of section 7.1 is therefore a mixture of two hardware generations as well as two networks; the per-vantage cut is where a single-host reading lives, and the pooled figure is not a property of either host; the per-vantage cut (section 7.1) is reported for that reason, and the software-version rule of section 6.7 applies across blocks as within each.

The T2 pre-run timing check and its stop rule. Before T2 block 1, a pre-run dry schedule is run on T2 (exploratory, the seed of section 9, its data never reused), and for each of its R10 payments the client's receipt read, the arrival of the batched response that completed the set (the end of clock, section 5.3), the finalized number in that response, the receipt's block and that block's own timestamp, the `x-upstream-id` of the completing response and the number of distinct backends that answered the payment's reads are printed (`python3 -m dim1.timing`). The confirmatory run proceeds only if, for every R10 payment with an end of clock, the completing response carries a finalized number at or past the receipt's block and arrives after that block's timestamp. If one does not, no confirmatory payment is made, and this pre-registration is amended by a dated addendum before any block runs; the rule is never silently re-tuned.

### 6.6 Assurance sweep

No sooner than two hours after the last trial of each block (a judgment: well past the time Base Sepolia's L1-derived `finalized` tag normally needs to cover a block, so the R1 covariate is readable for every payment), every observed payment of that block is re-read from its rail by one explicit check per rail: R1 receipt status and whether its block is covered by the Sepolia L1-derived `safe` and `finalized` tags; R2 Horizon `successful` (R2's end of clock is already a client-held Horizon read, section 5.3; as a diagnostic of the facilitator's own timing, every R2 payment's HTTP 200 time is also compared with the close time Horizon records for its ledger, and a 200 more than one second before that close is flagged and counted per rail); R9 `finalized` with no error; R10 receipt status of the client's own transaction, the server's returned hash re-read and compared with it (and its own receipt read where they differ, for every payment including the unverifiable-identifier ones), and the end of clock compared with the timestamp of the receipt's block. These R10 comparisons are reported and change no classification: the identifier is decided live, in the trial (section 5.5), and the end of clock already waits for the block to be finalized at the node the client reads (section 5.3); R11 sha256 of the preimage equals the payment hash in the invoice. A payment whose check cannot be completed is reported as unverifiable, not as settled.

Clock reporting for the R10 timestamp comparison. The comparison above places the end of clock on the runner's wall clock (the payment's wall-clock start plus the monotonic offset to the end of clock) and the block's own timestamp as Tempo records it, to the millisecond. The host clock is NTP-disciplined, and its offset from an NTP server (time.cloudflare.com, one SNTP query, retried up to three times if a packet is lost) is measured and logged at the start and at the end of every block, a reading still missing being reported, so a reader can judge the comparison. Neither the comparison nor the offsets classify any payment.

Orphan-settlement reconciliation, a reported diagnostic and not a scoring change. For every censored payment of a block, the same sweep searches the rail for a successful settlement from the firm's buyer to the firm's seller in the payment's window (from two seconds before it started to two minutes after; a judgment: the two seconds absorb the one-second resolution of chain timestamps and the host's clock offset, and the two minutes cover the 120-second timeout) that no recorded payment owns: an ERC-20 `Transfer` of the payment token on R1 and R10, a Horizon payment or token transfer on R2, an SPL token transfer signed by the buyer on R9. Each such settlement is assigned to at most one censored payment, the nearest after its start. R11's Spark transfers are not readable by address, so R11's censored payments are reported as not checkable. Per rail, the count of payments "censored by the client, settled on chain" is reported beside the observed and censored counts. Such a payment stays censored in pass@k and in the races, exactly as section 5.5 says: the agent was told it failed.

### 6.7 Stopping, pausing and drift

- The run is not stopped or restarted on the basis of any result.
- Blinding. During the run the orchestrator prints and computes no per-rail interval, percentile, pass@k or race outcome; it writes per-trial records only, and nobody reads them for results until the fourth block has ended. Mechanically: the orchestrator writes a block's end marker file only when the block has run to its end, and the report tool refuses to run on any confirmatory block whose end marker is absent. The report of section 7 is computed only after all four markers exist.
- Restarts. A runner is restarted only on one logged harness condition: it returned no result within the 120-second timeout (the orchestrator's wait of section 5.5). Because every runner reports by its payment's own primary-clock timeout, this fires only on a runner that has stopped answering; R10's later identifier event never triggers a restart. At most three restarts are made per block, all automatic, counted over the block's whole life: the count is read back from the block's own event record when it resumes, so a resume never resets it. Each restart is recorded with its cause and the rail whose runner needed it; the payment that timed out stays censored. If a fourth would be needed, the block ends: its end marker is written, and its trials not yet run (and any voided trial not yet re-run) are reported as not run, never as censored. The 1,500 paired scored payments of section 5.5 are then fewer by those trials, which are counted and reported; the realised races per pair per block are reported beside every per-pair figure, and the restarts beside them by rail (section 7.4).
- Wallet settle check. Before every block starts, and so at every block boundary, the orchestrator waits until no transaction is pending on the wallets the firm signs with on the EVM rails (R1's seller, R10's buyer: the pending and latest nonces are equal), rechecking every 30 seconds. The block starts automatically the moment they are equal. If the nonces still disagree at 60 minutes, a settle stop is recorded and the block does NOT start; the same 30-second poll continues, and the block starts by itself, with no operator step, the moment the nonces agree. The stop and its total length are reported. The funds stop below is a different kind of stop and is described differently: it ends the process at a trial boundary, stays blinded, and is resumed by a person after the top-up. A block never begins with a pending transaction, because a stuck nonce on a firm wallet would queue every later payment of that rail behind it and the no-remediation rule would forbid the cure. That reasoning holds for R1's seller. On R10 the check is weaker than it reads, and is disclosed as such: the pinned client signs each payment with an expiring nonce key and a `validBefore` at most 25 seconds after signing (read in the pinned SDK), so R10 payments do not advance the buyer's ordinary nonce and the nonce comparison cannot see a pending R10 payment; for the same reason a pending R10 payment cannot queue later ones, and it lapses within 25 seconds, so the hazard the rule guards against does not arise on R10. No human decision enters this rule. Both values are judgments: 30 seconds is several block intervals on both chains, so a recheck rarely misses a change by much; 60 minutes is long enough for a stuck test-network transaction to be mined or dropped in normal conditions, and short enough that a block never waits indefinitely. R11's wallet is covered by its settled balance read; R2's and R9's transactions are submitted by their facilitators, not by a firm wallet.
- Pause for diagnosis. The rule applies to the four RACED rails only; R9's censored share is reported (section 7.4) and never pauses a block, so a failure of the diagnostic rail cannot interrupt the races. If any raced rail's censored share over its own last 100 scored payments in the block (scored payments only: a voided payment never enters the window, and the void share per rail is reported in section 7.4) (or all of them, once there are at least 20) passes 20 percent, the block pauses at the next trial boundary. The pause lasts EXACTLY 30 minutes (a judgment: long enough to read one rail's logs and the chain, short enough to bound the disruption to a block). During it nothing in any measured path is changed: no runner or resource server is restarted, and no configuration, wallet, DNS or endpoint is changed; a change made during a pause voids the whole block: its trials are reported as not run, never re-run and never scored, and the breach is reported. The operator reads that rail's logs and the chain and writes a finding during the pause in a fixed template (rail, window, counts, what was read, hypothesis, action taken, which must be none); writing it does not shorten the pause. The block resumes automatically at 30 minutes, whether or not a finding was written, and the record says which; every runner then makes one warmup payment, recorded and never scored, exactly as after a restart (section 6.3). The configuration hash and the harness-manifest hash of section 16 are recomputed from what is on disk at pause entry and again at resume, and both pairs are logged; a difference detects an edit to the hashed configuration and harness files made during the pause, and is reported as a breach. The hashes detect nothing else: a runner or server restart, a DNS, endpoint or wallet change are conduct rules, read back from the run's event record (every restart, wallet read and endpoint probe is an event), not detected by the hashes. The rail's window is not reset by the pause: it continues across it, and the same rail cannot pause again until more than 100 further payments of its own have been made. Every pause is reported in section 7.4 with its length and its finding. The pause changes nothing in what was recorded: every payment before it stays as classified. The window of 100 payments and the 20 percent threshold are judgments, not derivations: the window is long enough that, once full, the rule needs at least 21 failures to fire, so a single bad minute cannot trigger it, and the threshold is high enough to fire on a failure mode rather than on ordinary test-network noise; no exploratory run was large enough to calibrate either value.
- Funds. Each rail's test balance is read once when a block starts; the R11 wallet balance is read once, settled (the wallet reports nothing locked and nothing incoming, and two reads five seconds apart agree), and never again during the block, because reading it means initialising the wallet, which disturbs it. The on-chain rails (R1, R2, R9, R10) are re-read, read-only, at each probe window. Between reads, every payment attempted is charged at a fixed conservative cost per payment (for R11, 118 sats: the 102 sats observed per payment in the exploratory runs, plus 15 percent, rounded up), and every R11 runner restart at 1,024 sats (a judgment, not a measurement: a deliberately generous allowance for a fresh wallet session, which no exploratory run priced). The 15 percent margins here and below are judgments chosen to absorb small fee variation, not derived. Before each trial, if either rail of the trial cannot cover one more payment, the block stops cleanly at that trial boundary, before any payment of the trial is sent, and records which rail and which balance; no race is ever started that a rail cannot pay. After the rail is topped up from its faucet, the block resumes at the same scheduled trial, with fresh warmups; the stop, the top-up and the resume are reported. The funding target before the run carries a 15 percent margin over the expected spend. A payment that nevertheless fails for lack of funds is censored, not removed.
- If any network's recorded software version changes during the run, results for every rail involved are reported separately for the trials before and after the change, and are not pooled.
- Beside the pause rule, the largest censored share over any 500 consecutive scored payments of each rail (its own payments, in schedule order, within a vantage's two blocks taken together) is reported.

## 7. Analysis plan

### 7.1 Reported, per rail, each rail separately

For each rail: pass@k at k = 2, 3, 5, 10, 15 and 20 seconds with Wilson 95% intervals (lower bound first); the number of payments attempted, observed and censored (paired scored payments only; unpaired payments of section 5.5 appear in the cold-inclusive cut alone); the 50th, 95th and 99th percentiles of the primary interval, censoring-aware: censored payments are right-censored at the timeout, 120 seconds on the primary clock (section 5.5), so these are the Kaplan-Meier estimates (with all censoring beyond every observed value, they equal the empirical quantiles of the sample with censored payments placed above every observation), and a percentile that falls among the censored payments is reported as not reached; the percentiles of the observed payments alone are shown beside them; the log-normal location and scale of the primary interval, fitted by censored likelihood (section 7.3), with bootstrapped 95% intervals; that censored fit is the headline log-normal, a not-estimable censored fit is reported as not estimable, and the fit to the observed intervals alone, shown beside it, never replaces it; P(settled given accept) with a Wilson interval. These are reported for the warm-only cut of the primary (full-envelope) interval, the cold-inclusive cut, and the companion (pay-command, DIM-02-consistent) interval, pooled across both vantages (500 races per pair). Beside them, the warm-only primary figures are reported for each vantage separately (750 payments per raced rail at each), as the frozen DIM-02 method reports each topology. R9's figures are the same quantities, computed the same way from its 2,000 solo payments (1,000 at each vantage), and are reported in a separate diagnostic table headed "Diagnostic, not raced", never in the results table of the four raced rails, because they were measured without a co-scheduled opponent and are not load-comparable (section 6.5).

This document states no expectation about how any rail compares with another.

### 7.2 Computed, not reported

The frozen v1.2 method computes Bradley-Terry strengths and a pairwise win matrix. This run computes them because the frozen method requires it, over the four raced rails only (R9 is in no race). They are not reported in any published artefact; the private file that holds them carries, beside every per-pair figure, the realised races per pair per block (section 7.4). ### 7.3 Bootstrap

The fit. The log-normal location and scale (and the implied median) are fitted by censored likelihood, the point estimate and every resampled set alike: each censored payment is right-censored at the 120-second timeout on the primary clock (section 5.5), and the location and scale maximise the likelihood of the observed intervals together with the probability that each censored payment exceeded 120 seconds. The maximisation is expectation maximisation on the log scale, as implemented in the harness (`dim1/analysis.py`): it starts from the fit to the observed intervals alone (location the mean of the log intervals, scale their standard deviation with divisor N, the maximum-likelihood divisor), with the starting scale floored at 10^-3 so that a set whose observed values are all equal can still be iterated; at each step the variance is floored at 10^-12; it stops when the location and the scale each change by less than 10^-10 between iterations. A fit that has not met that tolerance after 500 iterations is counted as unfittable, never reported from its last iterate. With no censored payment the fit is the ordinary maximum-likelihood fit, and a set whose observed values are all equal then has scale zero, reported as such. A set with fewer than two observed payments, the mathematical minimum for a two-parameter fit, is unfittable.

The headline. The censored fit is the reported log-normal of section 7.1. If it is not estimable (fewer than two observed payments in the cut, or a non-converging fit), it is reported as not estimable and the fit to the observed intervals alone never replaces it; the observed-only fit is always shown beside it, as a bracket, not a substitute. Right-censoring at 120 seconds treats every censored payment, including a hard rejection that never settles, as a slow settlement; that is a modelling choice, and it pulls the fitted location and scale upward when censoring is mostly rejections, which is why both fits are shown.

The resampling. The percentile block bootstrap resamples whole units of 10, 20 and 50 consecutive scheduled payments of the rail within one run block, the units of section 10. Units are formed from each payment's position among its rail's scheduled scored payments in its run block (positions counted before any exclusion), so a payment excluded by section 5.5 (a voided or unpaired payment) leaves a gap in its unit and the unit holds the rest; a unit left with no payment does not exist; a run block's last unit may be shorter than the length (the remainder unit) and is drawn like any other unit, carrying only the payments it holds. For a given cut, every unit of the rail across all its run blocks (and both vantages in a pooled cut) forms one pool; each of the B = 2,000 replicates draws as many units as the pool holds, uniformly with replacement, and concatenates their payments; the fit is made on that concatenation. The percentiles are computed over the fitted replicates only, which conditions the interval on fittability: the replicates dropped are those with too few observed payments, that is the most heavily censored ones, so the conditioning biases the interval toward faster and less dispersed intervals. The share of unfittable replicates is therefore reported beside every interval, per length, and a length with more than 5 percent of its replicates unfittable is not estimable (5 percent is a judgment: beyond it the interval describes too selective a subset of the replicates). The reported interval is, for each quantity, the widest over the three lengths, and only when all three lengths are estimable: if any length is not estimable, the interval is reported as not estimable (the conservative reading), with the per-length detail shown.

The seeds. As the harness computes them: a rail's base seed is the first eight bytes, read as a big-endian integer, of `sha256("<master seed>:analysis:bootstrap:<rail>")` for the pooled cuts, and of the same string with the cut's tag inserted before the rail for the per-vantage, per-block, per-opponent and after-funds-stop cuts (for example `analysis:bootstrap:T1-devbox:<rail>`); the single-payment bootstrap uses the base seed itself; the block bootstrap of the log-normal uses the base seed XOR 0x106 XOR the unit length, and the pass@k block bootstrap of section 10 uses the base seed XOR 0xB10C XOR the unit length; each drives Python's `random.Random`. The bootstrap that resamples single payments independently is reported beside the block bootstrap, never instead of it.

## 10. Sample size

The frozen trial count per pair is kept: 500 races per pair. With R9 outside the races, each raced rail (R1, R2, R10, R11) is in 3 pairs and has 1,500 scored payments; R9 has 2,000 solo payments. The check below uses the log-normal scale fitted to the exploratory runs of section 9 and is reported only as a check on those counts.

- Per raced rail, the widest Wilson 95% half-width of any pass@k on the frozen grid, at 1,500 payments, is at most about 0.024 for the rails estimated in shakedown part A, and about 0.022 for R11 from shakedown part B (24 payments; the fitted parameters are held in the exploratory store and are not restated here); the worst case for any rail (a proportion near one half) is about 0.025 at 1,500 payments.
- For R9, at 2,000 payments, the widest half-width is at most about 0.021 (worst case about 0.022).
- Per vantage (750 payments per raced rail, 1,000 for R9), the worst-case half-width is about 0.036 for a raced rail and about 0.031 for R9; the per-vantage cut is a check on the pooled figures, not a separate result.
- Per pair, 500 races detect a departure of about 0.063 from an even race (two-sided 0.05, power 0.8). These power figures are conditional on untruncated blocks: a block ended early (section 6.7) leaves fewer realised races in some pairs, which are reported beside every per-pair figure; pass@k and the Bradley-Terry fit are computed on the realised trials and tolerate unequal pair counts.
- The approximate standard error of the fitted log-normal scale at 1,500 payments is below 0.006 for every estimated rail.

These figures assume independent payments. Payments made over about a day share network and facilitator state, so the effective sample size may be smaller than the count. Three pre-specified checks follow from that:

- Dependence diagnostics, per rail and vantage, in schedule order: the lag-1 autocorrelation of the observed intervals (censored payments skipped), and the lag-1 autocorrelation of the binary series that is 1 for a censored payment and 0 for an observed one, over every payment, so that runs of failures are seen and censoring is not hidden by being skipped. Consequence: a rail whose lag-1 autocorrelation (either series) exceeds 0.3 at either vantage carries a dependence flag, and its robust intervals lead in any presentation regardless of width. The value 0.3 is a judgment: a lag-1 correlation of that size inflates the variance of a mean by roughly 1.9 times under a first-order autoregressive model ((1 + 0.3) / (1 - 0.3)), past which the independent-payment intervals are plainly too narrow.
- Block bootstrap: beside every Wilson interval for pass@k, a percentile block bootstrap interval is computed, with every censored payment entering as a failure at every k (exactly as in pass@k itself), at three pre-specified unit lengths, 10, 20 and 50 consecutive scheduled payments OF THE RAIL within one run block (units never straddle run blocks; each unit is resampled whole; 2,000 resamples per length, seeded per rail and length). A run block's last unit may be shorter than the length; it is kept as a unit, and the number of such remainder units is reported. At each k the widest of the three intervals is the robust interval, and only when all three lengths can be bootstrapped (a length needs at least two units); if any cannot, the robust interval is not estimable, no interval leads, and Wilson is shown labelled "assumes independent payments; the dependence-robust interval is not estimable for this cut", or, for a rail whose dependence flag is set (lag-1 autocorrelation above 0.3 at either vantage), "dependence detected for this rail at lag 1; the dependence-robust interval is not estimable for this cut; this interval assumes independent payments", never as the lead interval. The draw is the one stated in section 7.3: one pool of the rail's units per cut, as many units drawn per replicate as the pool holds, uniformly with replacement, remainder units drawn like any other, excluded payments leaving gaps. Where the robust interval is wider than Wilson's, it LEADS in any presentation and Wilson is shown beside it. The three lengths are a judgment, not a derivation: they span short-lived dependence (a few minutes of a rail's payments) to dependence lasting about an hour, the longest that still leaves enough units to resample (at 50, each raced rail has 375 payments per run block, so seven full units and one remainder unit per block, 32 units over the run; R9 has 10 per block, 40 over the run); taking the widest makes the choice conservative.
- Heterogeneity: two groups (the two vantages; block 1 against block 2 within T2; block 1 against block 2 within T1) are flagged as heterogeneous for a rail if EITHER their Wilson intervals of pass@k at k = 5 seconds do not overlap, OR their robust intervals do not overlap at any point of the frozen k-grid. The single Wilson point k = 5 seconds is a judgment: it is the middle of the frozen grid, and the grid-wide robust check stands beside it so that no other k escapes. A vantage flag on a rail makes its per-vantage figures lead in any presentation. A block flag is reported beside the rail's figures. Both block comparisons are confounded with run period (block 1 and block 2 of a vantage run at different times, and each T2 block is a fresh machine), so a block flag says that something differed between the two periods, not what.
- Pairwise vantage check, withheld: for each pair, the win share at each vantage is computed from the races, and a pair whose winner differs between the two vantages is flagged in the withheld file's report (section 13). The published report states only the COUNT of pairs whose winner differs between the vantages, never which pairs, since naming them would disclose the withheld ordering.

This run follows the frozen doctrine's principle (each rail's ecosystem-canonical reliance level) and ends R9's clock at `finalized` as the network reports it; it takes no 32-slot depth reading, which carries no security meaning under Alpenglow. The same principle would have been applied the same way had Alpenglow made R9 slower than the 32-slot reading: the choice followed the principle, not the number. Because the reliance level the frozen pin names does not exist on devnet, R9 is not raced against the other rails (section 3): its figures are measured on the same protocol and reported in a separate diagnostic table, beside the races, never in them. Its payments are made alone, without a co-scheduled opponent, so they are also not load-comparable to the raced figures (section 6.5). The devnet software version is recorded on every R9 sample. Diagnosed cause of the client-rejected, chain-settled R9 payments of the exploratory runs: the x402.org facilitator's own devnet RPC rate-limited it (HTTP 429), and the facilitator reported the payment as "settlement_pending" while the transfer settled; in the dry runs this was tripped by three back-to-back warmup payments within a few seconds. In the dry runs of revisions 6 to 9, R9's last warmup preceded its first scored payment by 45 to 89 seconds, and scored R9 payments are separated by at least the one-second pacing plus any trials scheduled between solo slots. That this spacing will not trip the limit is this document's own prediction, not a published property of the facilitator, whose limit is not known to this document; when one does, it is classified, counted and reported with its cause, and stays censored.
- **R10 Machine Payments Protocol on Tempo.** Moderato testnet, not Presto mainnet; the frozen method already registers the testnet figure as an optimistic bound. R10's end of clock is the completion of the body read of the one batched response on the Tempo Moderato RPC, from the pay command, in which a finalized head at or past the receipt's block, that block's hash and the client's own status-1 receipt all agree (section 5.3). The batch is one backend's view, as the single `x-upstream-id` on each batch response indicates without proving it; a backend wrong about finality, or a proxy splitting or cache-composing a batch, would not be caught, a limit conceded because the reading follows Tempo's documentation, not a specification. The end falls 0.25 to 0.44 seconds after the receipt read in the T1 dry runs of revisions 12 and 13 (section 9): that is one added round trip from the T1 host to the Tempo RPC, because the batch can be sent only once the receipt is held, so it is a property of this harness and of the vantage's network path, not of Simplex BFT; on another vantage it is that vantage's round trip. The finalized tag is Tempo's own documented way to read finality; what this document observes of it on this RPC, as its own observation and not as a documented guarantee, is that it trails `latest` by up to one block (section 9 gives the measured lag per exploratory payment), a lag that is now inside R10's interval. The assurance sweep re-reads the receipt, its block hash against the finalized chain, and the end of clock against the block's timestamp for every confirmatory payment, as reported diagnostics. The Stripe-mediated acceptance leg is not exercised.
- **R11 Machine Payments Protocol on Spark-Lightning.** Spark's hosted regtest: the hosted-operator ceremony is real infrastructure, while the underlying Lightning payment and its routing are simulated.
- **Test-only components inside the measurement, and what is not measured.** R1: the x402 facilitator is the firm's own in-process component, not a production facilitator. R2: the OpenZeppelin testnet facilitator. R9: the x402.org facilitator as it runs against devnet. R10: the Stripe-mediated acceptance leg, which production may use, is not exercised at all. R11: Spark's hosted regtest operators, with simulated Lightning routing. Every figure includes the behaviour of these components and says nothing about their production equivalents.
- **Vantage.** Two vantages (section 6.5): a devbox in England and a cloud machine in Falkenstein, Germany (Hetzner Cloud fsn1). They are network-distinct, which is the frozen DIM-02 bar (a named cloud region for the second), and geographically distinct as well, though both are in Europe; no claim is made about a client measuring from another continent. The confirmatory cloud machines have dedicated vCPU, so neighbour load does not enter their timings; the host-load covariate (section 6.5) is recorded on both vantages all the same, and the per-vantage cut (section 7.1) shows any remaining difference rather than hiding it.

## 14. Kickoff scoping record

- **Inversion.** How would this run mislead? (a) A start of clock that differs by rail, so that a rail gains or loses its challenge round trip or signing time: closed as to the start event by section 5.2; the interval contents differ by rail as the section 5.2 table states, and the companion interval lets a reader remove them. (b) An end of clock at different strengths of evidence: closed by the frozen per-rail doctrine plus section 5.3, where every rail's end of clock is the client's own evidence, on R1 and R10 watched from the pay command with nothing learned from the server, on R2 and R9 read once the server's 200 has disclosed the identifier (a path property, with the server's first-evidence stamp measured beside it), and disclosed where a test network no longer exhibits the frozen mechanism (section 11). (c) Dropping failures: closed by section 5.5. (d) Time-of-day or launch-order effects: closed by section 6.1. (e) A rail winning by doing less at the boundary: the assurance covariate, section 6.6. (f) Re-running until a favourable result: section 6.7 and the anchor.
- **Concept unity.** Settlement finality remains one shared concept across rails (irreversibility, judged at each rail's own reliance level); the dimension-design checklist found the per-rail doctrine valid for that reason. Re-confirmed for the test networks, with the R9 exception recorded in section 11.
- **Named disconfirmer.** If the per-rail pass@k curves of two rails cross between the warm-only and cold-inclusive cuts, between the two vantages, or between the software-version strata of section 6.7, the single-number reading of either rail's finality is not supported and the report says so.
